# Processed data: the shared feature matrix

Generated by `scripts/build_features.py` from the Kaggle files in `data/raw/`.
To regenerate: `python3 scripts/build_features.py data/raw data/processed`

## Files
- `catalogue.csv`: 9,025 movies + train/held-out split (8,171 / 854, seed 2026). Everyone uses this catalogue and this split.
- `movies_clean.csv`: one readable row per movie with all covariates (lists joined by `|`). Raw overview/tagline for text embeddings; lists for Jaccard sets.
- `features.npz`: the numeric matrix (see below). `features.csv` is the same matrix, not committed (31 MB).
- `builder.joblib`: places new movies in the same space.
- `blocks.json`: columns of each block and weights. `report.txt`: coverage. `dropped_films.csv`: 41 movies without metadata.

## How to load
```python
import numpy as np, pandas as pd
```

## What features.npz is
A table of numbers: one row per movie (9,025, same order as `catalogue.csv`), 733 columns, built only from movie features (no ratings). Similar movies (e.g. Toy Story and Toy Story 2) have similar rows, and the embedding methods start from these rows.

## Why those columns
- Categories are "multi-hot": one 0/1 column per value. TMDb has 20 genres, so genres = 20 columns. Toy Story has 1 in Animation, Comedy and Family, 0 elsewhere. A single column with a number per genre (Action = 1, Animation = 2, ...) would invent an order and distances between genres that don't exist. With one column per genre, a movie can have several genres, and two movies are closer the more genres they share.
- Same idea for language (10 most frequent + "other" = 11 columns) and saga (one column per saga with at least 2 movies = 408 columns).
- Keywords, actors (top 5), directors, writers and companies have thousands of different values: too many 0/1 columns, so each block is compressed with SVD to 30-50 columns. Text (overview + tagline) becomes TF-IDF word weights, compressed to 100 columns. Year, runtime and budget are 4 standardized numeric columns (budget 0 = missing, plus a budget-missing flag).
- Left out on purpose: popularity, vote_average, vote_count, revenue. They measure success, which is what the Plackett-Luce model has to estimate.
- Everything is fitted on training movies only; held-out movies are only transformed.

## Why block weights
Most methods compare movies through distances between rows, which add up differences column by column. Without correction, a block with many columns (text: 100) would dominate one with few (genres: 20). So the script:
1. rescales every block so that, on average, each one contributes equally to the distance;
2. multiplies each block by a weight (`WEIGHTS` in the script). A block's contribution to the squared distance scales with the weight squared: 1 = like the others, 0.5 = a quarter (language for now), 2 = four times, 0 = ignored.

The weights decide what "similar movies" means (higher genres: map grouped by genre; higher cast/directors: same authors close). There is no right value: start with equal weights, try a few alternatives, keep the one that does best in the shared evaluation, and justify it in the report.
